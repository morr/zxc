# Git Conventions

## Hard rules

- **Never add a Claude co-author trailer.** No `Co-Authored-By: Claude` (or any Claude-related trailer) in commits, regardless of who authored the changes.
- **Never chain `git add` and `git commit` with `&&` in one Bash call.** Use separate Bash invocations so each matches its own permission rule.
- **No `--no-verify`, no `--no-gpg-sign`.** If a hook fails, fix the underlying issue. Don't bypass.
- **Prefer new commits over `--amend`.** Amending changes the previous commit; if a hook silently failed and the commit didn't land, an amend hits the wrong target.
- **Never force-push without explicit user request.** Never to `master`/`main` even with explicit request — warn first.
- **Stage by name, not `-A` / `.`.** Spelling out paths avoids sweeping in `.env`, credentials, large binaries, or in-progress unrelated files.

## Commit message style

Style learned from `git log --author='Andrey Sidorov'`. Match it.

### Form
- **Imperative mood, lowercase first word.** `fix missing X`, `add Y`, `remove Z`, `replace A with B`. Not `Fix...`, not `Fixes...`, not `Fixed...`.
- **One subject line, no body.** Body is rare. Subject runs long only when class/key names demand it — e.g. `store Billing::KassaYandex::GetPayment payload by Payment::PayloadKey['get_payment'] key`.
- **No Conventional Commits prefixes.** Plain prose. No `feat:` / `fix:` / `chore:` / `refactor:` / `docs:`.
- **Many small focused commits.** Don't squash into umbrella commits. Each step in a refactor is its own commit so the iteration is visible.

### Verb vocabulary

- **Code change**: `fix`, `add`, `remove`, `replace`, `rename`, `move`, `update`, `convert`, `wrap`, `make`, `take`, `use`, `extract`, `store`, `cache`, `migrate`, `bump`, `return`, `set`, `fill`, `delete`, `disable`, `enable`, `allow`, `ignore`.
- **Bugs**: `fix X`, `bugfix`, `bugfix for X`. All three are interchangeable; prefer `fix X` when the X is short and known.
- **Reverts**: `Revert "..."` (auto-generated by `git revert` — leave as-is). For manual undo of own work, write `rollback X` (`rollback sentry related change`, `rollback one more sentry change`, `rollback template change`).
- **WIP / iteration**: `work on X`, `another X`, `more updates to X`, `additional X`, `continue X`, `finished X`, `X skeleton`. Use `work on X` freely — partial-work commits are normal here.
- **Test churn**: `fix specs`, `fix unstable specs`, `fix unstable spec`, `fix broken spec`, `fix broken tests`, `fix failed specs because <reason>`.

### "misc" prefix

Use `misc` when the change is a grab-bag of small unrelated tweaks, or too small to describe precisely.

Examples from history: `misc fix`, `misc rubocop`, `misc cleanup`, `misc improvements`, `misc improve`, `misc better naming`, `misc refactor`, `misc rename`, `misc tinkoff update`, `misc test page change`, `misc code formatting`, `misc url fix`, `misc change (to make search in the code easier)`. Bare `misc` is acceptable for truly miscellaneous.

Don't use `misc` when the change has a clean specific description — pick the description.

### Identifiers in subjects

- **Bare Ruby names, no backticks**: `Payment::TinkoffPayload`, `BoxesBestOfferQuery`, `Mutations::CreateAgreement`, `Payments::QrStatus`, `payment.bank_account`, `Agreements::CurrentBankAccount`, `Billing::KassaYandex::GetPayment`. Class/module/method names are common, the eye reads them fine without backticks.
- **Backticks for syntax-y or visually noisy values**: `` `СБП` ``, `` `&nbsp;` ``, `` `trailing_slash: true` ``, `` `ngenius` ``, `` `touch: true` ``, `` `in_debt` ``, `` `'<не указано>'` ``. Use when the value would otherwise blend into prose or contains punctuation that looks like sentence punctuation.

### Reasoning in subject

When the *why* matters and fits, append it with a comma, `because`, `so`, `in order to`, or a parenthetical:

- `make migrations to be much faster`
- `return activerecord scope from BoxesBestOfferQuery instead of array`
- `add 'touch: true' to multiple models so caching on frontend can work properly`
- `vcr update in order to prevent cassette mutations for bigquery requests`
- `misc change (to make search in the code easier)`
- `make 'ngenius' to be uncountable, so when rails singularizes it, it is still 'ngenius' instead of 'ngeniu'`

If the why doesn't fit, leave it out — don't add a body just to explain.

### Issue refs

Trailing `#NNNN` when the commit closes / addresses a tracked issue:

- `fix error when nulls returned for a row #7298`
- `Remove link "khranenie-shin" from footer #7323`

No leading `Fixes:` / `Closes:` keyword. The number alone is the convention.

### Multi-step refactor pattern

A big change typically lands as a series. Pattern from history (payload migration):

```
work on improvement of payload logic
PayloadKey constants
convert 'callback' payload usage to new syntax
convert 'webhook' payload usage to new syntax
convert 'refund' payload usage to new syntax
convert 'get_payment' payload usage to new syntax
fix specs
fix unstable specs
```

Each commit is one verb on one slice. Cleanups (`fix specs`, `misc rubocop`) get their own commits — don't fold them into the main commit.

## How to write a commit

1. Run `git status` and `git diff` (or `git diff --cached`) — see what's actually staged.
2. Run `git log -10 --oneline` — sanity-check style against recent commits before drafting.
3. Pick the verb (above).
4. State what changed in 3–10 words. Add the *why* only if it fits in the subject.
5. If it's a grab-bag, fall back to `misc <area>`.
6. Stage explicitly (`git add path/to/file …`), then commit in a *separate* Bash call.
7. Use a HEREDOC for the message to preserve formatting:
   ```
   git commit -m "$(cat <<'EOF'
   fix unstable specs
   EOF
   )"
   ```
8. After commit, `git status` to verify it landed (if a hook failed, the commit didn't happen — fix and create a NEW commit, do not amend).
