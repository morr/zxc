# ECS patterns used in ZXC

Copy these shapes. They are extracted from the codebase, not from generic Bevy advice.

## 1. Enum state + exclusive tag components

Every stateful entity carries **both** a plain enum field (readable, `Reflect`,
shows up in the inspector) and a **tag component** mirroring it (queryable, so
systems filter archetypally instead of matching in a loop).

The tags are generated by `exclusive_state_tags!`, which emits
`#[component(immutable, on_add = ..)]` types whose hook removes their siblings —
so "at most one state tag" is enforced by the ECS itself, whoever inserts.

```rust
macro_rules! pawn_states {
    ( $( ($name:ident, $state_component_name:ident) ),* $(,)? ) => {
        #[derive(Debug, Clone, PartialEq, Eq, Reflect)]
        pub enum PawnState { $($name),* }

        pub mod pawn_state {
            $crate::exclusive_state_tags!($($state_component_name),*);
        }

        impl Pawn {
            pub fn change_state(
                &mut self, new_state: PawnState, entity: Entity, commands: &mut Commands,
            ) -> PawnState {
                log_state_change!("Pawn({:?}).state {:?} => {:?}", entity, self.state, new_state);
                let prev_state = mem::replace(&mut self.state, new_state);
                // the on_add hook of the new tag removes the old one
                self.add_new_state_component(commands, entity);
                commands.trigger(log_event!(EntityStateChangeEvent(entity, self.state.clone())));
                prev_state
            }
        }
    };
}

pawn_states!(
    (Idle, PawnStateIdleTag),
    (ExecutingCommand, PawnStateExecutingCommandTag),
    (Dead, PawnStateDeadTag),
);
```

Rules that fall out of this:
- **Never insert or remove a state tag by hand.** Go through `change_state`, so
  the log line and `EntityStateChangeEvent` always accompany the transition.
- Query by tag, not by enum: `Query<&mut Pawn, With<pawn_state::PawnStateIdleTag>>`.
- Tags are `immutable` — `Query<&mut PawnStateIdleTag>` will not compile, by design.
- Same pattern exists for `Movable`, `Commandable`, `Workable`, `Farm`, `Restable`.

## 2. Guard macros instead of nested `if let`

```rust
fn on_rest_complete(
    event: On<RestCompleteEvent>,
    mut commands: Commands,
    mut query: Query<(&mut Commandable, &mut Restable)>,
) {
    let Ok((mut commandable, mut restable)) = query.get_mut(event.entity) else { return };
    let Some(ref command_type) = commandable.executing else { return };
    let CommandType::Sleep(SleepCommand { commandable_entity, .. }) = command_type else { return };

    commandable.complete_executing(event.entity, &mut commands);
    restable.change_state(RestableState::Activity, event.entity);
}
```

`let … else { return }` chains are the house style for observer preconditions;
the macros cover the state-comparison cases:

- `ensure_state!(fn: …)` returns, `ensure_state!(loop: …)` continues; both
  `trace!` the mismatch, which is what makes a bad transition visible in the log.
- `return_unless!` / `continue_unless!` are the silent variants — use when the
  mismatch is expected traffic, not a suspicious event.
- In an observer always use the `fn:` form; observers have no loop.

## 3. Observers over polling systems

```rust
// registration
app.add_observer(on_pawn_death.run_if(in_state(AppState::Playing)));

// handler — one event, no loop
fn on_pawn_death(
    event: On<PawnDeathEvent>,
    mut commands: Commands,
    mut query: Query<&mut Pawn>,
) {
    let PawnDeathEvent { entity, reason } = &*event;
    // …
}

// sender
commands.trigger(log_event!(PawnDeathEvent { entity, reason }));
```

- Handler naming is `on_*`; senders always wrap in `log_event!` so the run is
  auditable from the trace log.
- `On<E>` derefs to `E` — destructure it (`*event` when `Copy`, `&*event` otherwise).
  There is no `.event()` and no `.target()`.
- Choosing `Event` vs `EntityEvent`: see the `message-to-event` skill.

## 4. Commands as events

`commandable/` holds one file per command type — `feed_command.rs`,
`move_to_command.rs`, `pick_up_item_command.rs`, `sleep_command.rs`,
`to_rest_command.rs`, `work_on_command.rs`, `complete_task_command.rs`,
`drop_carried_item_command.rs`, `user_selection_command.rs` (9 variants of
`CommandType` in `components.rs`).

Each command is an `EntityEvent` targeting `commandable_entity`, handled by an
observer that drives the entity's `Commandable` state machine. Dispatch goes
through `CommandType::trigger`, which just `commands.trigger(log_event!(command))`s
the inner value — so every command is logged uniformly. Commands execute
sequentially per entity; completion goes through `commandable.complete_executing(..)`
and interruption through `InternalCommandInterruptEvent` /
`ReleaseCommandResourcesEvent`.

When adding a command: new file in `commandable/`, `EntityEvent` struct with a
`commandable_entity` field, observer registered in `commandable/mod.rs`, and a
new variant wired into `CommandType` (enum + `trigger` match).

## 5. Change detection and query filtering

```rust
// filter in the query, never in the loop body
Query<(&Pawn, &mut Transform), (With<pawn_state::PawnStateIdleTag>, Without<DyingMarker>)>

// only react to actual changes
Query<(Entity, &Restable), Changed<Restable>>

// resources
.run_if(resource_changed::<RootConfig>)
```

Reserve `Changed<T>` for work that is expensive or that would otherwise re-fire
every frame; state transitions already carry their own event.

## 6. Async work off the main thread

Pathfinding requests go through `async_queue` rather than running A* inline: the
requesting system pushes a request, a task computes it off-thread, and a polling
system applies the result. Any new multi-frame computation should reuse that
queue instead of blocking a system.

## 7. Components hold data plus their own invariants

Components are plain data with `impl` blocks for derived reads and guarded
mutation — logic that belongs to the datum lives with it, orchestration lives in
systems:

```rust
impl Restable {
    pub fn is_overflowed(&self) -> bool { self.fatigue >= FATIGUE_OVERFLOW }

    pub fn progress_fatigue(&mut self, time_amount: f32) {
        // reads config(), clamps to [FRESH, OVERFLOW]
    }
}
```

Inspector-visible components add `Reflect` + `InspectorOptions`:

```rust
#[derive(Component, Debug, InspectorOptions, Reflect)]
#[reflect(InspectorOptions)]
pub struct Restable { pub fatigue: f32, pub state: RestableState }
```

Note most ZXC components are **not** `Reflect` — which is exactly why BRP can
count them but not read their values (see the `live-app` skill).
